### Before you move on

SaaS complexity is mostly coordination: who owns data, who may act, what can be retried, and how usage is measured.

### Implementation notes

| Engineering move | Guidance |
| --- | --- |
| **Define tenancy** | Choose how tenant identity enters the request and how it is enforced. |
| **Separate identity from authorization** | A valid session does not automatically grant access to every tenant resource. |
| **Move slow work to jobs** | Email, exports, indexing, and model tasks need durable status. |
| **Instrument usage** | Record the signals required for limits, billing, and support. |

### Decision lens

| Mode | Practical emphasis |
| --- | --- |
| **Single tenant** | Optimize for clarity and simple local development. |
| **Multi tenant** | Make tenant scope explicit in every query and cache key. |
| **Enterprise** | Add auditability, stronger isolation, and operational runbooks. |

## UI Starter Kit SaaS

Jeston also ships an open-source UI Starter Kit for SaaS products at [`starter-kits/saas-ui`](https://github.com/jeffersoncampos12p-dev/jeston/tree/main/starter-kits/saas-ui). It is a complete runnable dashboard foundation rather than a mockup: it includes a responsive workspace shell, metric cards, project progress views, recent activity, a static project detail route, a projects JSON endpoint, a health endpoint, security headers, and a scoped cache configuration.

Create the same application through the CLI after installing Jeston 2.1.x:

```bash
npx @kvantjs/jeston create pulseboard --template=saas-ui
cd pulseboard
npm install
npm run dev
```

The generated application exposes these routes:

| Route | Responsibility |
| --- | --- |
| `/` | Workspace overview and operational dashboard |
| `/projects/:id` | Project detail generated with `getStaticPaths` |
| `/api/projects` | JSON collection to replace with a database-backed service |
| `/api/health` | Liveness response for local and hosted checks |

The kit intentionally ships with seeded data so a new project has a useful interface immediately. Before production, replace those fixtures with tenant-scoped queries, add authentication and authorization middleware, connect billing and usage events, and review the content security policy for any third-party assets. The kit is an application boundary, not a hosted identity, billing, or data-isolation service.

Its source is MIT-licensed and can be copied, extended, or used as a reference for a custom design system.
