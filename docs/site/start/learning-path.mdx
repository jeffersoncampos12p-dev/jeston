# Learning path

Ryvax is easier to learn when each new concept answers a concrete problem. Follow the stages in order if you are new to the framework; jump directly to the relevant stage if you are evaluating one capability.

## The progression

| Stage | Build | New question answered | Exit checkpoint |
| --- | --- | --- | --- |
| 1. First request | One page | How does a file become a response? | The page renders from a clean install. |
| 2. HTTP contract | One API route | How do methods, status, headers, and errors stay explicit? | `curl` and a test agree on the response. |
| 3. Route tree | Static and dynamic routes | How does Ryvax choose the handler? | `ryvax routes --json` matches the intended map. |
| 4. Data boundary | One provider adapter | What belongs to the app and what belongs to infrastructure? | The adapter can be replaced in a test. |
| 5. Identity and policy | Session plus authorization | Who is acting, and what may they access? | Unauthorized access fails independently of the UI. |
| 6. Async work | A retryable job | What happens after the request ends? | Retry, idempotency, and shutdown behavior are tested. |
| 7. Operations | Health, logs, and release checks | How will a team detect and recover from failure? | A clean artifact can be verified and rolled back. |

## Why this order works

The sequence moves from observable behavior to ownership decisions. Rendering first gives you a visible result. HTTP contracts then make the result callable. Routing explains how requests reach code. Data, identity, and jobs add state only after the lifecycle is understood. Operations closes the loop by proving that the artifact can be run by someone who did not write it.

Adding SQL, authentication, or AI workflows before the request contract is clear makes failures ambiguous. The same error could come from routing, authorization, a provider, or serialization. Progressive complexity reduces that ambiguity.

## How to use each guide

Every guide should answer four questions before you move on:

1. **What does the framework own?** Identify lifecycle, transport, compiler, or runtime behavior.
2. **What does the application own?** Identify domain policy, authorization, persistence choices, and user-facing semantics.
3. **What can fail?** Name malformed input, timeouts, cancellation, dependency loss, and shutdown behavior.
4. **What proves it works?** Choose a request, test, manifest, metric, or artifact that makes the claim observable.

If a page describes a feature without answering these questions, treat it as an unresolved design decision and continue to the related reference page before adopting it.
