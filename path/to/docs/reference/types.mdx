# Types reference

<Accordion title="Detailed background for this page" icon="book-open">

Use types to make lifecycle assumptions visible without pretending compile-time types validate network input.

**Expected outcome.** A readable contract for contexts, handlers, responses, errors, and adapter capabilities.

**Why this boundary matters.** Types reduce accidental mismatch between layers, but boundary validation remains a runtime responsibility.

### Page-specific implementation notes

- **Type the context:** Expose request ID, signal, deadline, params, and body deliberately.
- **Separate input and output:** Do not reuse a domain type as an unvalidated network schema.
- **Model errors:** Give callers stable categories and operators useful correlation.
- **Keep capabilities narrow:** Adapters should implement only the operations they promise.

### Page-specific failure questions

- **Why not trust TypeScript at runtime?:** Types are erased and cannot inspect untrusted JSON or headers.
- **What belongs in a result type?:** Success data, stable error category, and correlation metadata when useful.
- **How should optional fields behave?:** Define whether omission means unknown, default, or explicit absence.

</Accordion>

| Concern | Default posture | Review question |

> **Design note**
>
> A type is a promise made by code; validation is the evidence that the outside world kept it.

<Note>
Avoid broad `any` escape hatches at request and adapter boundaries.
</Note>
